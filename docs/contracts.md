# 输出契约：子代理交什么、怎么交

## 1. 为什么要有契约

父代理不能信任"自由文本"——收件必须机械化。契约 = 两个 JSON 文件 + 一套字段语义 + 证据纪律。

## 2. 两个文件

- **判断件**（文本层）：逐项给字段值
  `项目号、作者、原作、类型、系列名、集号、标签、角色、声优、原曲、引用 + 每个非空字段的依据`
- **漫游件**（在线层）：实体档案与出处
  `实体（作者/原作：名字、别名、主页、介绍）、出处链接、站点笔记、攻略更新、修正、下载候选`

**先写判断件、先落盘，再写漫游件**——两步分开落盘，任何一步死掉都不丢前面的产出。

## 3. 字段语义（要点）

- **作者** = 做作品的人（≠ 上传者、≠ 搬运者、≠ 标题里出现的人名）；
- **原作** = 被二创的 IP（角色所属的游戏/动画）；
- 类型、系列、集号、标签、角色……按固定枚举与格式；
- **每个非空字段必须附一句依据**：引材料原文或页面原文——这是最硬的一条纪律。

## 4. 实体档案

作者/原作是独立实体：名字、别名、主页（平台 + 链接）、介绍、关联项目。
批次只报增量；合并同名与别名走专门的合并操作（旧名转进别名表，显示名自动重生成）。

## 5. 修正通道

`修正 = [{项目, 字段, 新值, 理由}]`：改字段、留旧值、标记"修正"；新主名升主、旧主名降级。
定位：保险，不是主力——质量靠证据纪律与保守默认。

## 6. 结构化信息不让模型"转录"

页面上的标签/结构化元数据由**脚本从缓存里机械提取**，不由子代理手抄：

- 更全（模型会漏抄）；
- 更省（不占输出与上下文）；
- 更稳（源站的敏感词不经过模型输出通道，避免被内容过滤打断整个任务）。

子代理只负责"把页面抓下来、把 URL 记下来"。

## 7. 收件器的守卫

入库前过滤非人名形态：来源标记、规格串、日期、分类标签一律**不建实体**；取值有歧义时宁空勿错。
收件器与契约字段之间保持回归测试——契约变了、收件器没跟上，是出过事故的。
